# 设计：指针生命周期的可审计化

本页记录 0.2.0 的设计决策：任务指针从哪里借鉴了机制、为什么不引入更多机制、以及每条改动的验收标准。它解释"为什么"，字段级约束以 [协议](protocol.md) 为准。

## 1. 问题：单指针的三个静默失效

0.1.0 的运行时只有一份 `state.json`。`generation + revision` 的 CAS 保证了"写入不冲突"，但冲突解决只是可靠性的一个面。把指针当作长任务唯一可恢复事实源之后，剩下三个失效是静默的——它们不报错、不阻塞，只是让指针在无人察觉的情况下与现实脱节：

| 失效 | 表现 | 为什么危险 |
| --- | --- | --- |
| **陈旧** | 指针停留在 `revision=400` 的那次发布上，`updated_at` 是两小时前；模型一直在推进新内容 | 恢复时注入的是一份"过去某时刻"的目标，模型会照着已经作废的下一步干活，而且没有任何信号提示它这么做 |
| **原地踏步** | 每次 prompt 都成功发布，`revision` 稳步增长，但 `pointer_text` 逐字节不变 | revision 增长制造了"进度在推进"的假象；真相是模型没有产出新的下一步，或者任务已经卡住 |
| **清空即抹除** | `SessionStart(clear)` 或新任务开始时，旧指针被整体覆盖 | 上一个任务的目标、被放弃的原因、已经排除的方向全部消失；这正是压缩场景里最贵的一类信息 |

## 2. 借鉴的机制与出处

本仓库的两条参考实现各自解决了一部分同构问题：`billion-context`（ACP，Active Context Pruning）把"历史"当作可召回的不可变事实源，`dsh-argp` 把"该动什么"交给确定性规则裁决。以下是逐条映射，以及**我们没有抄的部分**。

### 2.1 历史是不可变事实源，上下文只是它的一个渲染视图

ARGP 的核心不变量是"append-only 日志是唯一事实源，上下文是日志的渲染视图"[^argp-readme]。指针场景完全同构：`state.json` 是**渲染视图**（当前生效的指针），而指针的变更历史应当另有不可变载体。

落地：新增每会话追加日志 `journal.jsonl`。每次成功发布、每次 fenced 清除各追加一条**元数据**记录（不存 `pointer_text` 正文）。`revision` 是串联视图与日志的 key。

选元数据而非正文，是因为指针正文最大 8192 字节，若逐版本留档会让日志随任务长度线性膨胀；而"谁在什么时候发布到哪一版"这类元数据，恰好是诊断上面三个失效所需的全部信息。正文需要时可从历史 state 恢复——本页 §3 说明为何这已足够。

### 2.2 守卫裁决：模型提议、确定性规则处置

ARGP 的 Stage-1 把"提取缺任一高信号 token 即整体拒绝""no-op 替换不落地"作为守卫规则，模型输出永远是不可信输入[^argp-readme]。指针侧的对应物是：`pointer_text` 由模型提议，但**是否能落地由确定性规则裁定**。

落地：发布路径上已有 CAS 守卫与 8192 字节上限；本版把"原地踏步"从隐患升级为**可观测事实**——日志记录每次发布的 `pointer_digest` 与 `pointer_byte_count`，于是"连续 N 次发布、正文逐字节未变"变成一条可查询的序列，而不是需要靠人翻 history 才能发现的异常。

我们**没有**做的是否决式守卫。ARGP 可以在 extract 缺 token 时整体拒绝，因为原子有可判定的"高信号 token"集合；指针正文是自由散文，任何"必须包含 X"式的硬断言都会在合法输入上误杀（例如一个 bug 修完之后，新指针本来就应该不再提那个 `file.ps1:275`；再比如任务目标从"修 A"演进为"改修 B"时就该删除旧 token）。因此本版只做**记账**：记下来，让模型和用户看得见，不替它们裁决。

如果日后的证据表明元数据信号不足，下一步是**顾问式**的 token 落差提示（在回执里列出"上一版有、这一版没有"的承重 token），而不是拒绝写入——同样的信息量，零误杀面。这个顺序是刻意的：先证明"指针在看不见的地方脱节"，再考虑要不要干预。

### 2.3 前缀稳定是生命线

ARGP 用前缀指纹测试证明"N 轮逐轮压缩后请求前缀稳定"，直指缓存经济[^argp-readme]。指针的注入点（`SessionStart`、`UserPromptSubmit`）在上下文里是稳定位置，注入内容逐字节变化同样会让该点之后的缓存失效。

落地：注入 envelope 的字段顺序、每行格式、换行规范固定；`revision` 未变时产物逐字节相同。新增前缀指纹测试锁定"revision 不变 ⇒ 注入字节不变"。

### 2.4 状态可观测

`/argp` 一屏给出预算、剪枝次数、召回命中率、cites 解析率[^argp-readme]。指针侧的对应物此前完全缺失：用户无法回答"hook 到底跑没跑、指针多久没更新、日志有没有缺口"。

落地：新增只读报告入口 `src/task-pointer-report.ps1`，输出状态、年龄、revision、日志深度与缺口计数、最近若干条日志。

### 2.5 被清空的记录不是垃圾

ARGP 的墓碑机制让被剪节点在上下文里留下可一跳召回的痕迹，并显式防止"墓碑再立碑"的链式劣化[^argp-readme]。指针侧的 `CLEARED` 正是一个墓碑：它应当留下"这里曾经有一个指针（revision=N，task=T）"的痕迹，而不是静默消失。

落地：fenced 清除追加 `EVENT=CLEARED` 记录，并带上被清除指针的 `task_id`、`revision`、`pointer_digest`。于是"我们为什么放弃上一个任务"从"永远丢失"变成"日志里查得到"。

## 3. 明确不做的三件事

**不存指针正文副本。** 日志只存元数据与哈希。理由：8192 字节 × 每次发布会让日志体积失控，而日志要解决的问题（陈旧、原地踏步、清空即抹除）只需要元数据。若将来需要正文时间旅行，正确的做法是为历史 state 加保留策略，而不是把每版正文塞进日志。

**不做自动剪枝与自动合并。** ARGP 的 Stage-2 可以用 0-LLM 图规则自动摘除入度为 0 的原子，因为原子间存在可判定的引用边。任务指针之间没有这种图结构：`revision=12` 的指针与 `revision=13` 的指针是同一个任务的连续快照，而不是可独立废弃的节点。自动剪枝在这里没有正确的判定依据，因此日志只追加、只轮转，不做语义淘汰。

**不改 state schema。** `state.json` 仍是固定 8 字段的 v3。新增信息全部落在日志侧车文件里，好处是：既有 state 无需迁移、CAS 语义完全不变、0.1.0 时代的读取器仍能读新写入的 state。日志缺失时运行时退化为 0.1.0 的行为（见 §4.3）。

## 4. 契约

### 4.1 日志记录

`journal.jsonl` 与 `state.json` 同目录，UTF-8 无 BOM、LF 结尾、每行一个 JSON 对象、全 ASCII。记录形状：

| 字段 | 说明 |
| --- | --- |
| `journal_version` | 固定 `1` |
| `session_id` | 会话 ID |
| `event` | `PUBLISH` 或 `CLEARED` |
| `revision` | 该事件产出的 state revision |
| `generation` | 该事件产出的 generation |
| `status` | 该事件产出的 status |
| `task_id` | 可空；`task_id` 为空时写 `null` |
| `pointer_byte_count` | 可空；正文 UTF-8 字节数 |
| `pointer_digest` | 可空；正文（LF 规范化后）的 SHA-256 小写十六进制 |
| `previous_revision` | 可空；本事件之前的 state revision |
| `previous_status` | 可空 |
| `recorded_at` | `yyyy-MM-ddTHH:mm:ssZ` |

`pointer_digest` 是"原地踏步"判定的唯一依据：连续多条 `PUBLISH` 记录哈希相同，即表示正文逐字节未变。

### 4.2 写入顺序与幂等

每次发布在**同一次 session 互斥内**按序完成：CAS 校验 → 原子写 `state.json` → 读回校验 → 追加日志。因此日志记录的顺序与 revision 顺序一致。

### 4.3 失败语义：日志永远不阻塞 CAS

`state.json` 是唯一不可丢失的事实；日志是辅助证据。因此：

- 追加失败**不**使发布失败，回执返回 `ok=true` 并附 `journal_appended=false` 与 `journal_error=<CODE>`；失败本身不落盘（日志此时可能根本不可写），因此它只存在于那次回执里；
- 报告入口不从日志反推失败次数，而是显示可判定的形状异常：`JOURNAL_INVALID_LINES`（无法解析的行）与 `JOURNAL_REVISION_GAPS`（相邻记录的 revision 不连续——可能是一次追加没落地，也可能是轮转把更早的记录裁掉了）；
- 日志不可读、缺失或损坏时，读取路径退化为 0.1.0 行为，不抛错。

### 4.4 轮转

日志超过 512 KiB 时轮转：保留末次 100 条记录重写，丢弃更早的记录。轮转是**有损**的，且这是刻意的：日志的用途是诊断近期发布行为，不是永久归档。

### 4.5 重复标记 DIRTY 不写盘

"这次 prompt 又会把指针标记为 DIRTY"不构成内容变化。若状态已经是 `DIRTY`，`UserPromptSubmit` 不再改写 `state.json`，也不递增 `revision`，但仍照常注入 CAS 基础。两个直接收益：

- `revision` 从"prompt 轮数"变回"指针内容版本"，可以当版本号读；
- `updated_at` 停在真正最后一次内容变更上，因此 `POINTER_AGE_SECONDS` 是可信的陈旧信号——0.1.0 里它会被每一轮 prompt 刷新，永远接近 0。

这是**幂等保护，不是否决式守卫**：模型提议的正文照常落地，只是"重复标记"这一动作不再产生新的状态版本。

## 5. 验收

| 编号 | 断言 | 覆盖点 |
| --- | --- | --- |
| D1 | 成功发布后日志恰好多一条，且 `revision` 与 state 一致 | §4.1、§4.2 |
| D2 | 日志记录不含 `pointer_text` 正文串 | §3 第一条 |
| D3 | 相同正文连续发布时 `pointer_digest` 相同、`revision` 不同 | §2.2 |
| D4 | 注入 envelope 在 revision 不变时逐字节相同 | §2.3 |
| D5 | 日志追加失败时发布仍 `ok=true`，且带 `journal_appended=false` | §4.3 |
| D6 | 日志缺失/损坏时不抛错，报告标记缺口 | §4.3 |
| D7 | 超过上限后轮转保留末次 100 条 | §4.4 |
| D8 | `CLEARED` 记录保留被清除指针的 `task_id` 与哈希 | §2.5 |
| D9 | 报告入口在无会话时输出 `ABSENT` 而非报错 | §2.4 |

## 6. 兼容性

- 读取器：`state.json` 形状不变，0.1.0 的读取器可读 0.2.0 写入的 state。
- 写入器：0.2.0 会把 0.1.0 留下的无日志状态视为"日志深度 0"，并在下一次发布时开始记录。
- 安装器：既有安装器流程不变；日志目录复用 `state.json` 的目录，无需新的路径配置。

[^argp-readme]: <https://github.com/yoza10635/dsh-argp> 的 README 与 ARCHITECTURE 文档：append-only 日志作为唯一事实源、守卫裁决模型提案、前缀指纹测试、`/argp` 状态面、墓碑一跳召回。本仓库只借鉴机制，不引入其任何依赖。
